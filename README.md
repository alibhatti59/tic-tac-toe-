# Tic Tac Toe — Agent-Driven Development Loop

A two-player Tic Tac Toe app built entirely through an AI-agent-driven
ticket-to-merge loop, submitted for the Shayan Solutions AI Automation
Engineer (Intern) coding evaluation.

**I did not hand-write the app.** Every line of `index.html`,
`styles.css`, and `script.js` was generated by an AI coding agent,
directed ticket by ticket. My role was scoping the tickets, prompting
the agent, and wiring the pipeline around it.

## The loop, end to end

1. **Tickets created in Linear via MCP** — the agent used the Linear
   MCP server to create all 8 initial feature/CI tickets (ALI-5
   through ALI-12) directly from a prompt, not typed in by hand.
2. **Fetch → develop → status update** — for each ticket, I prompted
   the agent to fetch the ticket from Linear, move it to "In Progress",
   implement it, commit with the ticket ID in the message, and move it
   to "In Review".
3. **CI (GitHub Actions)** — the agent wrote `.github/workflows/ci.yml`,
   which installs dependencies, runs the test suite, and does a
   build/lint check on every push and pull request.
4. **PR review** — the agent reviewed the CI-setup diff and posted
   real findings as a PR comment via the `gh` CLI (see PR #1). It found
   two genuine issues: CI used `npm install` instead of `npm ci`, and
   the "lint" check only covered two JS files, not HTML/CSS. Both were
   fixed in a follow-up commit on the same PR.
5. **Auto-merge** — a branch protection rule on `main` requires the CI
   check to pass. PRs are merged via GitHub's auto-merge once CI is
   green.
6. **Discovery step** — the agent scanned the repo for dead code,
   missing coverage, and risk areas, wrote findings to `DISCOVERY.md`,
   and opened corresponding Linear tickets (ALI-13, ALI-14, ALI-15) for
   each real issue: an accessibility gap in ARIA labels, missing DOM-
   level test coverage for game interactions, and an undefined input
   contract on `getWinningLine()`. It also correctly reported finding
   no confidently dead code, rather than inventing a finding.
7. **MCP server exposing the app** — `mcp-server/` is a FastMCP-based
   server exposing the app's source for introspection: `list_files`,
   `read_function`, `describe_state`, and `run_tests`. Asked "what does
   the win check do and where is the board state stored?" through this
   server, the agent correctly answered: `getWinner()` collects each
   cell's `textContent` into a 9-value array, passes it to
   `getWinningLine()`, which checks the 8 possible lines; board state
   lives directly in the DOM (`.cell` button `textContent`), with no
   separate JS board array, and `currentPlayer`/`gameOver` are
   module-level variables in `script.js`. That's a verified-correct
   answer, not a guess — see the screen recording.

## Which agent and MCP servers I used

**Agent: GitHub Copilot, Agent mode, in VS Code.** I did not have paid
Claude Code or Codex access at the time of this evaluation. The task
allows "Claude Code, Codex, or similar" — Copilot's agent mode is the
"or similar": it edits files, runs terminal commands, and calls MCP
tools autonomously, the same category of tool.

**MCP servers used:**
- `https://mcp.linear.app/mcp` (Linear's official remote MCP server,
  streamable HTTP transport) — for all ticket creation, fetching, and
  status updates.
- `mcp-server/server.py` (my own, stdio transport) — the app
  introspection server described above.

Both are configured in `.vscode/mcp.json` in this repo.

### Connecting to Claude Code and Codex

I did not have paid access to verify these live, but the same
`mcp-server/server.py` is transport-agnostic — the same stdio
connection works with any MCP client:

**Claude Code:**
```bash
claude mcp add --transport stdio tictactoe-introspect -- python mcp-server/server.py
```

**Codex** — add to `~/.codex/config.toml`:
```toml
[mcp_servers.tictactoe-introspect]
command = "python"
args = ["mcp-server/server.py"]
```

I'm confident these would work as-is since the server only depends on
the standard MCP stdio protocol, nothing Copilot-specific — but I'm
flagging clearly that only the Copilot connection was actually tested.

## What works vs. what's honestly unverified

**Verified, working, and shown in the recording:**
- Linear ticket creation, fetch, status transitions — all via MCP, all real
- Every feature commit — real commits, real pushes, no hand-edited app code
- CI running and passing on GitHub Actions
- A real PR review comment with genuine findings, followed by a real fix
- Auto-merge firing off a passing CI run
- The discovery step surfacing three genuine issues
- The MCP introspection server answering a real question correctly

**Not verified:**
- Claude Code and Codex MCP connections (config provided, not tested live)
- No cross-session memory, permission gating, or a second specialized
  agent — none of the stretch goals were attempted, given the time box

## Running it

```bash
# the app
open index.html   # or serve it with any static server

# tests
npm ci
npm test

# the MCP introspection server
cd mcp-server
pip install -r requirements.txt
python server.py
```
